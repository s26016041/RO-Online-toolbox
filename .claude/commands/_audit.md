# _audit（全專案稽核）— 每個功能都驗一遍、把「改版會壞」的寫法補掉、順手抓 bug

跟 `/_patchCheck` 的差別：那支是**官方改版後的急救**（哪裡壞了、怎麼修好）；
這支是**平時的體質檢查**（哪裡遲早會壞、哪裡寫得不夠穩、哪裡有 bug）。
沒有改版也可以跑，跑完應該留下「已修的」與「排好序的待辦」。

## ⛔ 動手前先記住三件 RO 專屬的事

1. **GameGuard：只讀不寫。** 稽核用的任何腳本一律唯讀記憶體。不准注入、
   不准寫記憶體、不准改 IAT —— 會當機或封號（[PKT-011]、[PKT-013]）。
   要送動作只能走**封包**（複製遊戲 socket，[PKT-012]）。
2. **記憶體讀得到 ≠ 有連線。** 斷線之後背包與角色狀態照樣讀得出來，那是上次
   登入的殘留（[MEM-029]）；選角畫面還會讀到「數值合理但名字空白」的殘渣
   （[MEM-030]、[MEM-035]）。判斷有沒有登入一律用 `ro_capture.find_server(pid)`。
3. **動作類（真的走路／打怪／喝水／換圖）會動到使用者的角色，動之前先講一聲。**
   讀取類（`verify_sigs`、`show_status`、`find_*`）沒有副作用，直接跑。

★ 大量輸出一律落地：每一輪的清單寫進 `reports/audit-<日期>.md`（`reports/` 已在
`.gitignore`），主控台只印結論（幾筆、前幾筆、判定）。

## 鐵律：不能弄壞功能

每一次改動之後**都要**把這串跑完才算數：

```powershell
.\.venv\Scripts\python.exe -m pytest -q     # 762 項，全綠才算
py main.py --selftest                       # 4 分頁建得起來＋道具／怪物表、圖示、封包擷取都在
```

⚠ `--selftest` 一定要走 `py main.py`（它會自己切到 venv）。`-m ro_toolbox` 會說
「No module named ro_toolbox」—— 套件在 `src/` 底下，是 `main.py` 插進 path 的。

位址層：遊戲開著時跑一次並**存快照**，之後就能離線重跑（RO 常常在維修，不要每次
都叫使用者開遊戲）：

```powershell
.\.venv\Scripts\python.exe tools\verify_sigs.py --save-snapshot reports\ragexe.snap  # 要開著遊戲
.\.venv\Scripts\python.exe tools\verify_sigs.py --snapshot reports\ragexe.snap       # 之後離線重跑
.\.venv\Scripts\python.exe tools\show_status.py                                      # 偏移層，人工對畫面
```

★ 改之前先**量一次基準**（舊寫法的輸出：位址、狀態、走幾格、殺幾隻），改完拿新舊
比對 —— 「一致」是唯一能證明沒弄壞的證據。

⚠ `pytest` 綠 ≠ 程式起得來。Qt 訊號槽會**吞例外**讓測試假通過，`py_compile` 也抓不到
NameError；分頁建構會起背景執行緒，沒走正常關閉流程會被 Qt 用 `0xC0000409` 打死，
症狀是「自檢每一項都通過了，卻回報失敗」（[ENV-005]「exe 崩在 0xC0000409」那條）。
所以 `--selftest` 一定要跑。

## 1. 覆蓋率：哪些寫法還不是「改版不會壞」的

⚠ 這個專案**沒有** coverage 稽核工具（姊妹專案 Angels 有 `coverage_audit.py`）。
目前只能用下面的 grep 手動盤，所以**每一輪都要把結果落地成報告**，才比得出上一輪
修掉了什麼。（「做一支 `tools/coverage_audit.py`」本身就是待辦第一名。）

照 CLAUDE.md 的資料來源優先序（記憶體 > AOB > 資源包抄本）逐項盤：

| 項 | 目標 | 怎麼盤 | 沒到位的處理 |
|---|---|---|---|
| ① 位址 | **100%** 走 `services/signatures.py` ＋ `services/aob.py` | grep `0x[0-9A-Fa-f]{6,}` | 一定要補；沒有例外 |
| ② 結構偏移 | 能做成 `CodeSignature` 就做；不能就要有**出處註解** | grep `+ 0x`／`OFFSET`／`_OFF` | 見下面的判斷順序 |
| ②a A−B 距離 | ⛔ **一律是債**，不管註解寫得多好 | grep 兩個全域相減 | 立刻改成程式碼特徵 |
| ③ opcode／代碼 | AOB 救不了，但出處與**怎麼重驗**要寫 | `core/ro_protocol.py` 的常數 | 註明「用 `watch_packets.py` 重驗」 |
| ④ 寫死的遊戲資料 | 記憶體有同一份就**別抄 RODATA** | grep 內嵌的 id／名稱表 | 先問「遊戲載進記憶體了沒」 |
| ⑤ 打包資產 | `assets/` 是使用者電腦上的**唯一來源**（spec 收整個目錄，不會漏檔） | `mapdata.available_maps()`（要 > 900）、`icons.available()`、`item_name(501)` | 沒重建／沒 commit = 所有人手上都是舊資料，而且看不出來 |
| ⑥ 檔案存在性 | ⛔ 不准拿「檔案在不在」當判斷 | grep `.is_file()`／`.exists()` | 改問資料層（`has_terrain()` 是正例） |
| ⑦ 同一個位址寫兩份 | 只准有一個來源 | 同一個立即值／偏移出現兩處 | 合併；否則位移後一份會安靜落後 |

⚠ `--selftest` 驗的是道具表／怪物表／圖示／樣式表／封包擷取，**不驗地形**。
地形壞掉會讓走路類功能全滅（自動打怪不漫遊、自動尋路直接停用），所以第 ⑤ 項的
`available_maps()` 要自己跑一次，別靠自檢。

### grep 出來的東西怎麼分堆（不要一看到 hex 就當債）

實測 `src/ro_toolbox` 有 51 筆六碼以上的 hex，**絕大多數是雜訊**。分三堆：

- **雜訊**：註解／docstring 裡記載出處的位址（`實機讀出 0x123CD58`）、遮罩與
  NTSTATUS（`0xFFFFFFFF`、`0xC0000409`、`0xC0000004`）、PE 旗標（`0x20000000`）、
  範圍界線（`0x400000 < value < 0x10000000`、`_MAX_ADDR`）。→ 不動。
- **正例**：特徵裡當錨的位元組（`_MAGIC_DIV34`）、`signatures.py` 裡寫「怎麼生成、
  實機幾處命中」的條目。→ 不動，但確認 `verify_sigs` 有涵蓋。
- **債**：程式碼**執行路徑上**直接拿來當位址／偏移用的裸數字。→ 修。

### 偏移要不要做成特徵？判斷順序

1. **遊戲自己有沒有寫入／讀取那個值的程式碼**？有 → 做成 `CodeSignature`，
   從那道指令的立即值讀回來（`POSITION_X_SIGS`、`NAVI_DEST_SIGS`、
   `SUBMITTED_ACCOUNT_SIGS` 都是這樣）。⚠ pattern 裡那個立即值要自己寫 `??`，
   不准拿答案當錨（tautology，`.data` 一位移就整段失敗）。
2. 找不到唯一的指令錨 → 在 `tools/verify_sigs.py` 加一條**不變量**
   （值域、兩條獨立的路要對上、跟另一個來源交叉比對，像 `y-x==4`）。
3. 兩者都做不到 → 在常數旁邊寫清楚「為什麼不行」與「壞掉會怎樣」。
   **沒有註解的裸偏移一律當債。**

⚠ [MEM-006] 說「座標前 0x30 bytes 全是 0，做不出樣式」講的是**資料**樣式；
**程式碼**樣式沒這個問題。看到「資料做不出樣式」不要就退回寫死，先去找引用。

⚠ 已知不算債的：遮罩／NTSTATUS／PE 旗標、`MAX_`/`MIN_`/`LIMIT_` 開頭的界線值、
`injector.py`（那是給**沒有** GameGuard 的遊戲用的，RO 走不到）。

## 2. 功能驗證：讀得到 ≠ 做得到

`show_status.py` 與各分頁驗**讀取**。動作層一定要補這一刀，而且每一項只認**硬證據**：

| 功能 | 送什麼 | 唯一算數的證據 | 副作用 |
|---|---|---|---|
| 走路 | `0x035F` | 收到 `0x0087` **且**記憶體座標真的變（單次上限 17 格，[PKT-030]） | 移動幾格 |
| 攻擊 | `0x0368`→`0x035F`→`0x0437`(act=7) | 收到傷害封包 `0x08C8`/`0x02E1` 或怪血 `0x0A36`（[PKT-035]） | 打一隻怪 |
| 死亡判定 | — | `0x0080` 的 type 位元組 = 1（**不准用等待時間**，[PKT-021]） | — |
| 撿東西 | `0x0362` | `bag.read_bag()` **現查**，數量真的 +1 | 背包多一格 |
| 喝水 | `0x00A7` | 收到 `0x01C8`，且**回包裡的道具編號等於預期的那個**（[PKT-036]） | ⛔ 消耗一瓶 |
| 跨圖尋路 | 走路＋傳點 | 記憶體地圖名換到下一張；[MEM-044] 傳點禁區要「走出去」 | **角色被送走** |
| 自動登入 | 見 [PKT-046] | 真的進遊戲，角色名讀得到（**選角畫面寫進去的**，太早讀是殘渣，[MEM-035]） | 佔用帳號 |
| 自動回連 | — | 新 PID 起得來，且**設定接得回去**（存身分不存位置，[DAT-028]） | 重開遊戲 |
| NPC 對話 | 對話封包 | 選項一律**文字比對**，不准猜編號（[DAT-027]） | 觸發 NPC |

一次跑完整輪（會動到角色，先要授權）：

```powershell
.\.venv\Scripts\python.exe tools\farm_test.py <pid> --seconds 70
```

印走了幾格、卡住幾秒、擊殺／撿取幾個、經驗每小時；軌跡在
`reports/farm_test_<pid>.json`。**跟上一輪的數字比**，差太多就是有東西壞了。

⚠⚠ **「封包送得出去」不代表遊戲做了事。** 對太遠的怪送攻擊伺服器不會幫你走過去
（[PKT-032]）；角色瀕死／死亡時完全不能移動而 bot 看不出來（[PKT-033]）；
攻擊送出後再送移動會取消連續攻擊（[PKT-034]）。**只認傷害封包與座標變化。**

## 3. 抓 bug：先照這張「這個專案實際踩過的坑」掃一遍

不是泛泛的 code review —— 下面每一條都在這個專案真的發生過，而且**症狀都跟根因
離很遠**。掃的時候一條一條對著找：

| 坑 | 長什麼樣 | 出處 |
|---|---|---|
| A 全域減 B 全域 | 改版後兩邊位移不同 → 座標回 `(0,0)`，而合理性檢查只擋 `>=512`，**(0,0) 通過了驗證**，A* 起點跑去地圖角落，全程不報錯 | [MEM-039] |
| 命中多個就放棄 | 6 個命中裡 5 個是堆積垃圾（HP 15／maxHP 42 億／名字空白），真的那個也在裡面 → 使用者看到「遊戲明明開著卻讀不到」 | [MEM-041] |
| 存位置不存身分 | 背包格號會遞補（丟／賣／用完一疊），存的那一刻沒錯，錯的是三分鐘後 —— **安靜地喝錯東西** | [MEM-028]、`potion._slot_of()` |
| 讀得到 ≠ 還連著 | 斷線後背包／角色狀態照樣讀得出來；選角畫面的角色名是殘渣 | [MEM-029]、[MEM-030]、[MEM-035] |
| 睡幾秒當機制 | 「等 1.5 秒讓它穩定」機器慢一點就整個錯位，失敗時看不出哪一步壞 —— 現存實例：`farm_page.py` 回連後 `QTimer.singleShot(3000, restore_into)`，分頁沒長出來就只留一行 warning | CLAUDE.md、[PKT-021] |
| 切包吃掉封包 | 黏在同一個 TCP 分段後面的封包**全部看不到** →「送了沒回應」其實是回了 | [PKT-043] |
| 換圖不重綁 | 換地圖／換頻道後 socket 與地形失效，擷取會**安靜地全瞎** | [PKT-038]、[PKT-040] |
| 錯誤只記 DEBUG | DEBUG 沒開就**完全看不到**，外面看到的是「送了 145 次的鬼打牆」，真正原因一個字都沒留 | `auto_login.py` OTP 段 |
| 每拍重掃 AOB | 自動補水變慢的真兇是 `bag.as_dict()` 每次呼叫都重掃一次 | [MEM-043] |
| 模組列舉卡死 | `EnumProcessModulesEx` 對掛 GameGuard 的 Ragexe 會卡住不回來 → 背包／封包長度表一起瞎 | [MEM-031]、[MEM-034] |
| Qt 執行緒沒收尾 | 「Destroyed while thread is still running」→ `0xC0000409`，看起來像打包壞掉 | [ENV-005]（「exe 崩在 0xC0000409」那條，編號有重複） |
| exe 沒簽章 | GameGuard 擋打包後的 exe 做大量記憶體讀取（錯誤碼 5）；`tools/sign_exe.py` | [ENV-006]（「GameGuard 擋 exe」那條，編號有重複） |
| 別的 onefile 挖我們的 `_MEI` | 開場清 `%TEMP%\_MEI*` 會把還在跑的程式挖空 | [ENV-007] |
| 檔案在不在當判斷 | `gat_path(name).is_file()` 在使用者的電腦上永遠 False = 功能全滅 | CLAUDE.md、`mapdata.has_terrain()` |
| ID 用猜的 | RO 的 opcode／道具編號不照系列連號。留空＝安全退化，填錯＝很有自信的錯 | CLAUDE.md、[DAT-024] |

★ 每抓到一條，先問「**同樣的寫法還有沒有第二處**」—— 上面好幾條都是復發型的。

## 4. 有沒有更穩的寫法（只在「能證明等價」時才改）

判斷標準只有三條，缺一不改：

1. **更少的失效面**：寫死 → AOB、抄 RODATA → 讀記憶體、全掃 → 指標路徑／特徵。
2. **失效時更安全**：安靜做錯 → 大聲停用／安全退化。
3. **能證明等價**：舊寫法與新寫法在**現在這台**上輸出一致（跑基準比對）。

已完成的例子（可以照抄這個做法）：

* `StatusOffsets.position`：寫死「HP 全域 − 0x3AD5FC」→ `POSITION_X/Y_SIGS`
  用座標**寫入端的指令骨架**定位，x/y 兩個立即值互驗且 `y-x==4`（[MEM-039]）。
* `input_helper.SUBMITTED_ACCOUNT_OFFSET`：寫死 `0x11D2ACC` → `SUBMITTED_ACCOUNT_SIGS`
  （`push 2718h` + `mov ecx,[ebx+0B4h]`，[MEM-032]）。
* `input_helper.SHARED_INPUT_OFFSET`：實測**沒有任何程式碼引用得到**，而且沒人在用
  → 直接刪掉，知識留在註解裡。**定位不了又用不到的東西，最好的處理是刪。**
* 尋路目的地：本來讀錯全域 → 用「**誰在引用它**」抓出真的那個（[MEM-046]）。
* 封包長度表：寫死表 → 從程式碼抽 936 個 opcode，改版自動跟上（[MEM-024]）。

⛔ **不要為了漂亮而改。** 這個專案的每一段怪寫法幾乎都有血淚註解，動之前先讀那段
註解與對應的 GAMEDATA 條目；沒讀懂就別動。

## 5. 收尾

* **一次 commit 一件事**，訊息寫清楚「原本會怎麼壞、改成什麼、怎麼證明沒弄壞」。
* 確認過的事實**兩個地方都要寫**：`GAMEDATA.md`（含走不通的路，舊條目**改狀態不刪除**）
  ＋ `~/.claude/projects/.../memory/`（一件事一個檔，只留「該去看哪裡」）。
* 沒做完的留成**排好序的待辦**（寫進 memory，別留在對話裡）。
* push 前三件事：`pytest -q` 全綠、看一遍 `git status` 的未追蹤檔案
  （⚠ **封包擷取輸出是明文，登入那包裡有帳號與認證位元組**；`封包/`、`*.etl`、
  `qr.jpg`、`RODATA/`、`reports/` 都已在 `.gitignore`，**新出現的同類要順手加進去**）、
  重建過的 `assets/*.gz` 一起 commit。
* 要發版走 `/_pushReleases`（⚠ 建 Release 前要先問過使用者）。
